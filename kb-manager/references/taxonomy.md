# docs 知识分类法

## 分类定义

| 类型 | 回答的问题 | 应该写什么 | 不应该写什么 |
|---|---|---|---|
| `guide` | 我要做 X，怎么做？ | 有隐性前置条件、顺序或验证要求的步骤 | README 已经说明的简单命令 |
| `rules` | 必须遵守什么？ | 项目约束、边界、必须同步的规则 | lint 已经强制的普通格式 |
| `reference` | 事实是什么？ | 业务语义、历史约定、构建/CDN 等速查事实 | 可由代码直接生成的清单 |
| `decisions` | 为什么这样设计？当前采用了什么取舍？ | 独立的选择、背景、权衡、后果或已确认的架构方向 | 没有决策依据的普通架构清单、为凑数量虚构的历史原因 |
| `gotchas` | 别人踩过什么坑？ | 症状、根因、解决方式、预防措施 | 普通编译错误和未验证传闻 |

## 判断流程

```text
这条信息能从代码、类型、路由或配置直接读出吗？
├── 能 → 不写
└── 不能
    ├── 是操作步骤 → guide
    ├── 是强制约束 → rules
    ├── 是稳定事实速查 → reference
    ├── 是选型或架构取舍 → decisions
    └── 是历史故障或隐性陷阱 → gotchas
```

## 归属判断

```text
是否适用于用户指定组织中的多个仓库？
├── 是 → 按 prompt 写入共享页面
└── 否
    ├── 只适用于当前仓库 → 写入仓库页面
    └── 只适用于子仓库 → 写入子仓页面
```

同一条知识不能在多个页面重复维护。需要复用时通过链接连接，不复制正文。

## decisions 拆分规则

- `decisions/` 可以包含多个页面；页面数量由独立决策主题决定，不设固定数量，也不默认只保留一个页面。
- 一个页面只记录一个独立决策。Nuxt 升级方向、layer 与宿主组合、双站点产物等主题
  的证据和影响面不同，应分别成页；只有同一决策的不同说明才合并。
- 代码能证明当前实现，但不能证明历史原因时，记录“当前实现边界”和可验证后果，
  明确没有历史评审证据；不要写虚构的备选方案、评审结论或时间线。
- 用户明确的架构方向可以作为决策来源，必须在正文中区分“用户确认的方向”和
  “代码当前状态”；不要创建 `source` 字段或 YAML 元数据。
- 决策页不因当前只有一个候选主题而强行创建其他页面；也不因后续扫描只命中一个
  页面而删除其他已有决策。

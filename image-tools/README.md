# image-tools｜图片工具箱

本 skill 定位是**图片处理工具箱**：把"图片该多大、该什么格式、压完糊没糊"这类判断固化下来，让 AI 直接给出可替换的产物。
这个 skill 目前做的是**网页图片优化**：在屏上看不出差别的前提下把像素数降下来。
网页上的图片通常比它在页面上真正需要的大得多：一张 2848×1600 的 banner，在手机屏幕上只占 240×108 CSS 像素。
这个 skill 按图片的**实际显示尺寸**重新出图，顺手转成 WebP/AVIF、裁掉显示不到的部分，
再拿结果和"原图在浏览器里的渲染效果"对比一次，确认压完没有变糊——这一步是导出流程内置的**清晰度强校验**，
掉得太多会自动升档重压，救不回来就直接告诉你"这几张保留原图"。

转格式、压尺寸、裁剪这三件事可以单独做，也可以一起做；批量目录、透明图、EXIF 方向、ICC 色彩描述都能处理。

## 一、能做什么

| 你想做的事 | 这样说就行 | 它会怎么做 |
| --- | --- | --- |
| 页面图片太大 | 「商品列表页那个 banner 图 2.8 MB，帮我压一下」 | 量出实际显示尺寸，据此出图并转 WebP，给出体积与解码内存的前后对比 |
| 批量转格式 | 「这批 png 都转成 webp，尺寸和内容别动」 | 只换容器格式，像素尺寸与解码内存不变 |
| 压完被反馈发糊 | 「测试说上一版图片压糊了，帮我看看问题在哪」 | 对比原图与候选的清晰度，指出该提导出尺寸还是提质量 |
| 出多倍图 | 「按 3 倍屏出图」 | 按屏上像素宽（显示宽 × DPR）再乘 `--supersample` 导出，默认 2 倍 |
| 评估体积 | 「帮我看看这个目录的图片费不费内存」 | 列出每张图的尺寸、体积、解码内存与建议动作 |
| 只压不改格式 | 「别转格式，只把尺寸压下来」 | 保持原 png / jpg，只缩放或只裁剪 |
| 归档要无损 | 「这批截图要归档，不能有损失」 | 用无损 WebP 输出，并逐像素确认与源一致 |
| 透明图要 JPEG | 「客户只要 jpg，但素材是透明 png」 | 按指定底色合成背景，而不是留下黑边 |

## 二、怎么用

在 Claude Code / Codex 里用一句自然语言说需求即可，例如：

- 「商品列表页那个 banner 太大，帮我按实际显示尺寸压一下」
- 「把这批 png 转成 webp，尺寸先别动」
- 「测试说上一版图标压糊了，帮我查一下」
- 「低端机滑动很卡，帮我看看是不是图片解码吃内存」
- 「压完帮我把产物替换回 src/assets/img，然后重新构建」

把图片位置（目录或单张文件）告诉它就能开始。不知道图片在页面上显示多大时，可以让它去页面里量——
给它选择器或页面地址即可；拿不到浏览器时它会读 CSS 推断，并提醒 transform / zoom 可能带来的偏差。

有三件事值得先知道：

1. 它不会改你的源文件。默认导出到独立目录，确认之后再替换；替换前建议先备份。
2. 默认输出 WebP，扩展名会变（`hero.png` → `hero.webp`），组件里的引用要一起改。
   不想换扩展名就说一句「保持原格式，只压尺寸」。
3. 导出时会自动做清晰度强校验：单张图掉超过 4.0% 就升档重压（先提质量，再提尺寸），
   最多换 2 个方案；换完仍不达标的那几张会在报告里标 `✗`，并打印原因、以退出码 4 结束——
   产物照样生成，但结论是这几张别替换。

## 三、它怎么判断

浏览器渲染一张图分下载与解码两步。文件体积决定下载耗时；**解码内存由像素数决定**（宽 × 高 × 4 字节），
与压缩率无关。一张 2848×1600 的图解码后约占 17.4 MB，即使压到几百 KB 也不会变。
低端设备上通常先撞到的是解码内存，而不是下载量。

| 指标 | 由什么决定 | 影响 |
| --- | --- | --- |
| 文件体积 | 像素数、编码质量、格式 | 下载耗时与流量 |
| 解码内存 | 像素数（× 4 字节） | 滚动流畅度、内存压力 |

所以导出宽度不取 1:1 的屏上像素，而取它的 2~3 倍：浏览器把大图缩小渲染时会做高质量降采样，
只给 1:1 反而要靠放大插值。实测把 2848×1600 压到 480×216 后，高频细节下降约 5.7%，肉眼可辨；
保留 3 倍超采样时下降约 1.4%，基本看不出来。

## 四、效果参考

下表是照片型素材的实测结果，你的素材收益取决于内容（照片类收益大，纯色、线条、截图类另说）：

| 你要的效果 | 典型结果 |
| --- | --- |
| 只转 WebP，不动尺寸 | 1.2 MB 的 JPEG → 约 260 KB；11.1 MB 的 PNG → 约 660 KB，解码内存不变 |
| 按显示尺寸压 + 转 WebP | 1.2 MB 的 JPEG → 约 40 KB；单张解码内存 17.4 MB → 1.6 MB |
| 一批图一起处理 | 六张合计 341 KB → 195 KB，解码内存 59.9 MB → 9.5 MB |
| 想要更小体积 | 同一张图转 AVIF（有损）约 113 KB；AVIF 的无损 Pillow 无法输出，脚本会直接拒绝 |
| 必须无损 | 11.1 MB 的 PNG → 8.5 MB 无损 WebP，像素与源完全一致 |
| 保持原格式，只压尺寸 | 六张合计 341 KB → 208 KB（体积下降，解码内存同步下降） |
| 压过头了 | 导出时自动检出：单图掉超过 4.0% 就升档重压；救不回来直接给结论"保留原图" |

这些数字与 [references/measured-data.md](references/measured-data.md) 同源；"单张"与"六张合计"来自两批独立测量，别互相换算。

## 五、首次使用准备

只需要 python3 与 Pillow（唯一依赖）。执行 `python3 -m pip install --user Pillow` 即可；
系统 Python 报 externally-managed 时，改用 `python3 -m pip install --break-system-packages Pillow`。
Windows 上是 `py -3 -m pip install Pillow`（详见下面的 Windows 小节）。

装完跟 AI 说一句「跑一下自检」就行，它会确认 WebP / AVIF / JPEG / PNG 四项支持情况。
缺依赖时脚本会直接把上面的安装命令打出来；AVIF 需要 Pillow ≥ 11 且编译了 libavif，不满足时改用 WebP 即可。

### Windows 上怎么用

脚本本身跨平台，命令只有三处不同：

| macOS / Linux（bash） | Windows（PowerShell） |
| --- | --- |
| `python3 "$S" export ...` | `py -3 $S export ...` |
| `--out /tmp/img-out` | `--out $env:TEMP\img-out` |
| `SKILL_DIR="${CODEX_HOME:-$HOME/.codex}/skills/image-tools"` | `$S = "$env:USERPROFILE\.codex\skills\image-tools\scripts\optimize_images.py"` |

- 装依赖：`py -3 -m pip install Pillow`（`py -3` 换成 `python` 也行）。
- 路径写反斜杠或正斜杠都可以（`C:\img\out` 与 `C:/img/out` 等价）；含空格的记得加引号，例如 `--out "C:\My Images\out"`。
- 报告里有 `✗`、`→` 这些符号：脚本启动时会把自己切成 UTF-8 输出，老式 cmd（cp936）和重定向到文件都不会因为编码报错。
- 用软链把 skill 挂进 `~/.codex/skills` 需要管理员权限或开发者模式；不想开就直接 `Copy-Item -Recurse` 拷目录。
- `doctor` 里 `sips` 显示"未安装"是正常的——那是 macOS 自带工具，Windows 上用 `magick` 或 `cwebp` 替代。

### 不想装 Python 依赖时的替代路线

脚本是纯 Pillow 实现，没有魔法。不想装 Python 时，等价的替代是：

| 目标 | 替代工具 | 说明 |
| --- | --- | --- |
| 批量转 WebP | `cwebp`（libwebp 官方 CLI） | `cwebp -q 90 -resize 960 0 in.png -o out.webp`，与 `--quality` / `--max-width` 一一对应 |
| 无损 AVIF | `avifenc --lossless` | Pillow 做不到真无损 AVIF，只有官方 CLI 可以 |
| 批量几何处理 | `magick`（ImageMagick） | `magick in.jpg -resize 960x -quality 90 out.webp` |
| Node 项目内联 | `sharp` | 构建期直接出多倍图，思路与 `--supersample` 一致 |
| 实时转换 | OSS / CDN 图片处理参数 | 不落盘、按 URL 参数出图，适合图片源不在仓库里的场景 |

代价是"清晰度对比"这一步没了：替代工具都不会拿结果与原图的渲染效果比一次，压糊了只能靠人眼发现。
`doctor` 会顺带检查上面这些外部工具装没装。

## 六、常见问题

**会不会把我原来的图覆盖掉？**
不会。产物写在独立目录里，目标路径和源文件重合时脚本会报错退出；同一批里出现重名冲突时整批中止，
不会只处理一半。替换由你决定，回滚就是拿备份覆盖回去。

**压完反而更大了？**
多半是纯色、线条、截图类素材，或者你说的是「保持原格式、只裁剪」。这类内容换成默认组合
（转 WebP + 降尺寸）通常就正常了；纯色和线条图其实更适合改用 SVG。

**转成 JPEG 后透明背景变黑了？**
JPEG 不支持透明通道，默认用黑色合成。可以指定底色（比如白色或品牌色）；透明素材更推荐留在 WebP / PNG。

**被说发糊怎么办？**
直接说「再清晰一点」。它会提高导出尺寸倍数或质量重新出一版，并再对比一次。
如果是它自己压糊的，导出时的强校验已经会拦下来：最多换 2 个方案——先提质量到 `--quality 95`，
再提尺寸到 `--supersample 3`；换完还是不行，它会明说"这几张保留原图"并给出原因
（通常是源图本身像素就不够，得换素材）。

**导出后的那份报告在哪看？**
就是 `export` 打出来的控制台输出，分成三块：前面的体积 / 解码内存对照表、中间的「清晰度强校验」小结
（每张图走到哪一档、`✗` 标出没通过的、以及一行结论）、后面的注意事项。
没通过的原因写在标准错误里（和警告混在一起），产物目录在输出末尾给出。

要给 CI 或别的程序读，加 `--report-json /path/report.json`：同一份结论会写成 JSON，
里面有逐图的档位链、掉多少、`passed` 与原因，以及一个 `fidelity.action`（`replace` 还是 `keep_original`）。
目前没有单独的 `report` 子命令——报告是 `export` 的副产品，跑一次导出就拿得到。

```json
{
  "fidelity": { "action": "keep_original", "passed": false, "mean_drop": -5.1,
                "drop_limit": -4.0, "max_retries": 2, "keep_original": ["hero.jpg→hero.webp"] },
  "images": [
    { "label": "hero.jpg→hero.webp", "out_size": [480, 216], "drop": -5.1, "passed": false,
      "retries": 2, "reasons": ["已换过 2 个方案（先提质量、再提尺寸）仍不达标"],
      "attempts": [ { "supersample": 1, "quality": 60, "drop": -8.2 },
                    { "supersample": 3, "quality": 95, "drop": -5.1 } ] }
  ]
}
```

（示例只列关键字段、数值为示意；真实条目里每个 `attempts` 还带 `cap_w` / `size` / `bytes`，
顶层还有 `target`（box / dpr / format / quality…）和 `summary`（体积、解码内存、变大的图…）。）

**照片明明是竖的，导出后躺倒了？**
带 EXIF 方向标记的照片会先转正再裁剪，导出结果不带方向标记，方向和你在浏览器里看到的一致。

**verify 报的像素差 12，远大于 3，是不是出问题了？**
不是。像素差只在"同尺寸、同重采样路径"下才有可比性：无损同尺寸导出实测 0.00，只要候选降过尺寸，参考和候选走的就是两条重采样路径，相位差会把数值推到 10 以上。结论看边缘能量均值。

**AVIF 能无损吗？**
不能。Pillow 的 AVIF 编码器没有无损开关，传了会被静默降级成有损，所以脚本直接拒绝这个请求——
要无损请用 WebP，确需无损 AVIF 得在外部用 avifenc 转换。

**为什么它说我的图不要压？**
因为这几张压了不划算，甚至更糟：源图已经是 WebP 或已经压过（重复编码会变大）、像素数已经贴着显示尺寸（再缩必糊，该换更大的源图）、或者压缩后体积反而变大（纯色 / 线条 / 截图类转有损、"保持原格式"只裁剪）。
这时它会给出结论和原因，而不是把变大的产物交给你。收益低于 5% 时也会提示"继续压没意义"。

**能用在 CI 里吗？**
可以，脚本只用标准库和 Pillow，参数错误、覆盖源文件、重名冲突都会以非 0 退出码失败；
清晰度强校验不通过时以退出码 4 结束，所以"这批图别上线"是可以当门禁用的。
再加上 `--report-json` 就能拿到机器可读的逐图结论与原因，不必解析控制台文本。
预览图片仍然需要有图形界面的环境。

## 七、已知限制

- 裁剪是居中裁剪。主体不在画面中心时结果可能被切到，先看一眼图，或者说「不要裁剪，只压尺寸」。
- 一次按一组显示尺寸处理。同一页里尺寸差异很大（hero 图 + 小图标）时建议分批，避免一种比例套所有图。
- 清晰度校验对压缩伪影不敏感，「可以替换」的结论仍建议目视确认一次。
- 拿不到浏览器时显示尺寸靠读 CSS 推断，遇到祖先元素上的 transform / zoom 会有偏差。
- 目录扫描只认 webp / jpg / jpeg / png / avif；gif、svg、bmp、heic 等会被**静默跳过**，不报错也不提示，批量处理前先用 `analyze` 确认张数对得上。
- 清晰度强校验只在 `export` 里生效，结论是文本 + 退出码（通过 0、判断该保留原图 4）；机器可读版本要
  显式加 `--report-json`，不加就只有文本。`verify` 本身不阻断，无论结论如何都以 0 退出，也没有 JSON。
- Windows 兼容是按跨平台写法实现的（路径归一化、控制台 UTF-8、PowerShell 命令），但回归用例目前只在
  macOS 上跑过；Windows 首次使用建议先 `py -3 $S doctor` 加跑一遍自带用例，确认环境没问题。

## 八、Roadmap：接下来会补什么

定位是图片工具箱，但目前只有"优化"这一条流水线跑通。下面按**能消掉多少人工步骤**排序，不按算法难度排序：加一个 Pillow 滤镜很快，真正省时间的是少一次手工返工。

### M1：把几何与体积控制补全（纯 Pillow，不引入新依赖）

| 能力 | 计划形态 | 现在为什么不行 |
| --- | --- | --- |
| 旋转与翻转 | `--rotate 90/180/270`、`--rotate -3.5 --expand`（任意角度并补边）、`--flip h/v` | 目前只在读图时按 EXIF 自动转正，没有主动旋转 |
| 裁剪位置可控 | `--crop-gravity top/left/...`、`--crop 960x540+120+80`、`--crop-focus x,y` | 只有居中裁剪，主体不在中心会被切掉（见"已知限制"） |
| 精确尺寸与留白 | `--exact WxH`、`--resize fit/fill/stretch`、`--pad-color`、`--max-height` | 只有按宽度上限缩放，做不出"必须正好 750×750"的规格图 |
| 图标多尺寸导出 | `--sizes 16,32,48,180,192,512` → `favicon.ico` + `apple-touch-icon` + PWA 图标集 | 现在得手工跑好几轮再改名 |
| 目标体积模式 | `--max-bytes 200KB`，自动二分质量逼近目标 | 只能给 `--quality`，最终多大靠猜 |
| 缩放后锐化 | `--sharpen`（unsharp mask） | LANCZOS 降采样比浏览器降采样偏软，边缘能量指标天然吃亏 |
| 元数据清理 | `--strip-exif`（默认保留，按需清） | 目前一律保留 EXIF / ICC，带定位信息的图不便对外发布 |
| 自动去白边 | `--trim` | 运营给的素材常带多余白边 |
| 跳过文件要有提示 | 扫描时打印"跳过 N 个非支持格式"，并支持 `--include-gif` 之类 | 现在 gif / svg / heic 是静默跳过，容易让人以为全处理了 |

**验收标准**：新增参数都有回归用例；`SKILL.md` 的「能力边界」里对应的条目同步删掉；缺口回填本节的对应行。

### M2：接进项目工作流（收益最大，也最需要设计）

| 能力 | 计划形态 | 价值 |
| --- | --- | --- |
| 自动量显示尺寸 | 扫描代码里的图片引用 + CSS，推断每张图的实际显示尺寸 | 省掉"开浏览器量选择器"这一步，这是当前最费人的环节 |
| 引用自动改写 | 产物扩展名变化时（`.png` → `.webp`）同步改 `import` 与 `src` 字符串 | 现在靠人肉 grep，漏改就是线上 404 |
| 项目级配置 | `.imagetoolsrc`：目录默认 box / dpr / quality、忽略列表 | 免得每次敲一长串参数 |
| 增量处理 | 按内容 hash 跳过未变素材，支持 `--changed-since HEAD` | 大仓库批量时不必每次全量重跑 |
| srcset 整套产出 | `--srcset 320,640,960,1280 --formats webp,avif,jpg`，并可生成 `<picture>` 片段 | 响应式图片从"手写一堆"变成一条命令 |
| CI 门禁 | `--check`：一条命令给出断言式结论 | `export` 已有退出码 4 + `--report-json`，够单独接；`verify` 仍不阻断、也没有 JSON |
| 可视化报告 | `--report` 生成原图 / 候选并排预览页 | 评审时不用在两台机器之间来回看 |

**验收标准**：在一个真实仓库上跑通"扫描 → 出图 → 改引用 → 校验 → 出报告"，中途不需要人工填 `--box`。CI 门禁要先定义清楚"什么算失败"（体积超标？边缘能量低于阈值？），否则会变成天天误报的噪音。

### M3：格式、素材来源与内容处理（按需引入依赖）

| 能力 | 依赖 | 说明 |
| --- | --- | --- |
| HEIC / HEIF 读取 | `pillow-heif` | 处理 iPhone 素材的高频痛点，当前输入只支持 webp/jpg/png/avif |
| 动图处理 | Pillow 动画 API 或 ffmpeg | GIF / APNG / WebP 动画的帧级优化与互转 |
| SVG 栅格化出图 | `cairosvg` / `resvg` | 只做"按 DPR 导出 PNG"；SVG 本身的优化仍走 svgo |
| 色彩管理 | 无（ImageCms） | 统一转 sRGB，避免浏览器渲染偏色 |
| 水印 | 无（Pillow） | 文字 / 图片水印，位置、透明度、平铺 |
| 区域模糊 / 马赛克 | 无（Pillow） | 截图打码，比手工开图省事 |
| 调色与滤镜预设 | 无（ImageEnhance） | 亮度 / 对比度 / 饱和度，是否有价值看具体场景 |

# 方法论：判断标准与取舍

命令和默认值在 [SKILL.md](../SKILL.md)，原始数字在 [measured-data.md](measured-data.md)。本文件回答的是"默认值不适用时怎么想"。

## 一、先判断瓶颈，再决定动作

图片在浏览器里分两步：**下载**（由文件体积决定）和**解码**（由像素数决定，宽 × 高 × 4 字节，与压缩率无关）。
低端机上先撞到的通常是解码内存，而不是下载量。

| 现象 | 瓶颈 | 动作 |
| --- | --- | --- |
| 首屏慢、流量大、CDN 成本高 | 文件体积 | 转 WebP/AVIF、降质量 |
| 滑动卡顿、低端机内存溢出、Tab 崩溃 | 解码内存 | **必须降像素**（换格式无效） |
| 图被反馈糊 | 像素给少了 | 提 supersample 或 quality，然后重新 verify |

判断顺序不能反：先按现象定位瓶颈，再选参数，最后验证。凭"文件变小了"收工是本 skill 最常见的误用。

**取舍顺序是清晰度 > 解码内存 > 体积。** 体积是前两者达标之后的副产品，不是第一目标：图糊了要返工一轮，多几十 KB 没人会在意；反过来"只在极限省流量"的场景才值得为体积牺牲一点清晰度，而且必须先 verify 确认牺牲没被看出来。

## 二、目标尺寸怎么定

```
屏上像素宽 = 显示宽(CSS) × DPR
导出宽度上限 = 屏上像素宽 × supersample（默认 2，稳；3 最锐）
```

为什么不是 1:1：浏览器把大图渲染到比自身小的尺寸时做的是高质量降采样，等于超采样抗锯齿；只给到 1:1，
它就只剩放大插值。实测把 2848×1600 压成 480×216 q80 后边缘能量掉 5.7%，肉眼可辨；保留 3 倍超采样只掉 1.4%。

为什么到 3 倍就该停：1440 宽相对 960 宽的边缘能量已经持平（都是 98.0%），但体积和解码内存继续涨。
超过 3 倍只在极限需求（例如要留给系统二次缩放）时才值得。

显示宽 240、DPR 2 时，supersample 2 = 960px = CSS 宽的 4 倍——**别把 supersample 和 CSS 倍率混为一谈**。

## 三、转格式、压尺寸、裁剪是三个独立维度

三者可任意组合，也可以只做一件。脚本把它们做成独立开关，就是为了让你一次只改一个变量。
格式默认不动（保持源格式），要转得显式传 `--format`：

| 只做一件事 | 参数 | 结论 |
| --- | --- | --- |
| 只转格式 | `--format webp --no-crop --no-resize` | 只影响下载体积，解码内存不变 |
| 只压尺寸 | `--no-crop --max-width N` | 体积和解码内存一起降，性价比最高 |
| 只裁剪 | `--no-resize --box WxH` | 通常得不偿失：体积反而涨（实测 +49%），解码内存只降 23% |

**一次只动一个变量**，否则指标变化无法归因——这也是排查"压完发糊"时最省时间的做法。

## 四、格式怎么选

| 素材 | 选择 | 原因 |
| --- | --- | --- |
| 照片、渐变、复杂纹理 | 转 WebP（显式 `--format webp`），更小就 AVIF | 有损压缩收益最大 |
| 纯色、线条、图标、截图 | 保留 PNG，或改用 SVG | 转 JPEG 会变大（实测 1.4 KB → 21 KB） |
| 带透明通道 | WebP / PNG / AVIF | JPEG 没有 alpha，只会按 `--flatten-color` 合成底色 |
| 已经是 WebP | 只调尺寸或质量 | 再"转 WebP"没有任何收益 |
| 需要归档、不能有损失 | `--format webp --lossless` | 只有 webp / png 能真无损；且**有损源再无损编码不会更清晰**，只是保持原样 |

## 五、清晰度怎么判

`verify` 的结论基于**边缘能量**：把原图和候选都按"浏览器会怎么渲染"重采样到屏上尺寸，再比高频细节。

- `export` 把同一判据内置成了**清晰度强校验**：单图下降超过 4.0% 就换方案重压，**最多 2 次**
  （先 q95、再 supersample 3）；换完仍失真则在报告里标 `✗` 并给原因、以退出码 4 结束。
  只换两个方案是有意的：两个变量各提一次就到头，再折腾代价成倍涨却未必更清晰。
  `verify` 留给复核、比对已有产物、以及候选不是本脚本导出的场合——两者数字同源，不会给出互相矛盾的结论
- 逐图噪声约 ±1.5%，所以看整批均值：<−3.5% 偏糊，−2.5%~−3.5% 临界，其余可替换；逐图只在 <−5% 时报警
- 这个指标偏保守：源图越清晰高细节，降到 960 会经历两次重采样，指标天然吃亏
- 它对**压缩伪影不敏感**（块效应、色带），所以"指标达标"之后仍要目视确认一次
- **平均像素差**只在"同尺寸、同重采样路径"下可比：无损同尺寸导出是 0.00；候选降过尺寸后，
  它和参考走的是两条重采样路径，相位差会把该值推到 10 以上。别拿 <3/255 去卡降过尺寸的候选

## 六、什么时候不该优化

这几类请求应该先说明再动手，而不是照着默认流程走一遍：

- **素材是 SVG、图标字体**：这是代码原生图形，该走 svgo 之类的代码手段，栅格化压缩只会变糊
- **图已经接近目标尺寸**（analyze 显示过采样 <1.2 倍）：再压就要牺牲清晰度，说清代价让用户决定
- **图片在 CDN 或有多处引用**：先确认引用处数与缓存策略，避免只改一半、版本对不上
- **用户要的是"更清晰"而不是"更小"**：本流程解决的是体积；源图本身不够清晰只能换源
- **用户只想"随便压一下，别折腾"**：可以少说，但不能跳过 verify 与备份（见 SKILL.md 的铁律）

判断"不该压"的硬指标，命中任意一条就如实报告、不要替换：

| 指标 | 怎么拿到 | 说明 |
| --- | --- | --- |
| 源图已是 WebP / 已压过 | `analyze` 看格式；`export` 后看体积 | 重复编码会变大（实测 webp→webp q90 体积 +69%） |
| 过采样不到 1.2 倍 | `analyze` 的"倍率(宽)"列 | 再缩必然发糊，该换更大的源图 |
| 压缩后体积变大 | `export` 的"体积下降"为负 | 纯色 / 线条 / 截图转有损、"保持原格式"只裁剪 |
| 源图宽度小于目标宽度 | `export` 的"源分辨率不足"提示 | 脚本不放大，压缩救不了，要换更大的素材 |
| 同格式有损重编码且省不到 15% | `export` 的"有损重编码"提示 | 默认保持源格式时，有损源（JPEG/WebP/AVIF）都属于这一类：多掉一次画质的买卖，建议保留原图 |
| verify 均值低于 −3.5% | `verify` 整批均值 | 升档重试仍不达标就别替换 |
| export 退出码 4 | `export` 的强校验结论 | 单图换满 2 个方案仍没过，结论同样是保留原图 |

- **用户要的是本 skill 没实现的操作（旋转、水印…）**：优化部分照做；额外操作可以用外部工具或一次性脚本帮他做完，但要说清那是权宜手段、不是 skill 能力

## 七、常见判断的实测依据

完整表格见 [measured-data.md](measured-data.md)，这里只列结论：

- 960 宽 q90 这一档：边缘能量 98.0%，单张 37 KB，解码内存 1.6 MB
- 480 宽 q90：96.6%，已接近可感知；同尺寸下 q80 只有 94.3%
- 只转 WebP 不动尺寸：JPEG 1.2 MB → 259.8 KB；PNG 11.1 MB → 660 KB（解码内存不变）
- 默认组合（保持源格式，压尺寸 + 裁剪）：六张 341 KB → 208 KB
- 同样参数加 `--format webp`：JPEG 1.2 MB → 40.3 KB，解码 17.4 MB → 1.6 MB
- 照片转 PNG：109 KB → 1.6 MB（反向优化）

# 实测数据与阈值来源

本文件是 `image-tools` 里所有数字的唯一出处：README 与 [SKILL.md](../SKILL.md) 只引用结论，改默认值或阈值时改这里。

## 测量条件

- 显示框 240×108 CSS px、DPR 2 → 屏上像素 480×216
- 素材是一组六张照片型图片，其中最大的一张 2848×1600（JPEG 1208 KB，解码 17.4 MB）；六张合计解码内存约 59.9 MB
- "边缘能量"是与"原图在浏览器里的渲染效果"比，下降越多越可能被说发糊
- 表里会同时出现"单张"与"六张合计"：它们来自两批独立测量，不要互相换算

## 档位参考

| 导出 | supersample | 代表作体积 | 六张合计 | 解码内存/张 | 边缘能量 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 480×216 q90 | 1 | 11.5 KB | 80 KB | 0.4 MB | 96.6%（−3.4%） | 偏省，接近可感知 |
| **960×432 q90** | **2** | **37 KB** | **208 KB** | **1.6 MB** | **98.0%（−2.0%）** | **推荐默认** |
| 1440×648 q90 | 3 | 72 KB | 316 KB | 3.7 MB | 98.0%（−2.0%） | 边际收益已趋零 |
| 原分辨率 2848×1282 q95 | 6 | 255 KB | 710 KB | 13.9 MB | ≈100% | 只在极限需求时 |
| 原分辨率 2848×1282 无损 | 6 | 1079 KB | 3.2 MB | 13.9 MB | 100% | 基本不值得 |

口径：**"代表作"指六张里那张 2848×1600**，"六张合计"是整组结果，单张 × 6 不等于合计。
表格里的百分数是代表作的逐图值，整批均值见下一节。写 2848×1282 而不是 1600，是因为 supersample 6 时
宽度上限已超过源图，脚本默认不放大，于是按显示比例裁成 2848×1282。

同一档位下 `--quality` 也影响观感：480 宽在 q80 时边缘能量只有 94.3%，换 q90 就到 96.6%。

## 阈值来源（verify 的判定线）

- 被用户判"发糊"的档位：整批均值 −4.0%（480 宽 + q80），其中代表作逐图 −5.7%
- 用户认可的档位（960 / 1440 宽 + q90）：整批均值 −1.2% ~ −2.0%
- 逐图噪声约 ±1.5%，所以判定线取：**逐图 <−5% 报警，均值 <−3.5% 判偏糊、−2.5%~−3.5% 判临界**
- 该指标以"源图单步降采样到屏上尺寸"为理想参考，偏保守；源图越是高清高细节，降到 960 会经历两次重采样，
  指标天然吃亏，此时直接上 `--supersample 3`

## 清晰度强校验（export 的自动升降档）

`export` 内置了与 `verify` 同源的强校验：每张图落盘后立刻按"浏览器会怎么渲染"比一次边缘能量，
单图下降超过 **4.0%** 就判失真，**最多再换 2 个方案**重压；换完仍失真则在报告里标 `✗`、打印原因，
并以退出码 4 结束（产物保留，结论是保留原图）。

| 常量 | 值 | 取这个值的依据 |
| --- | --- | --- |
| 单图失真线 | **−4.0%** | 比 verify 的逐图报警线（−5%）收紧一档，交付前就拦住；逐图噪声 ±1.5%，再紧会开始误杀 |
| 质量上限 | q95 | 比默认 q90 高一档；实测 480 宽从 q80 换到 q90 边缘能量 94.3% → 96.6%，质量档对小图很敏感 |
| 尺寸上限 | supersample 3 | 1440 宽相对 960 宽边缘能量已持平（都是 98.0%），再往上只涨体积和解码内存 |
| 重试上限 | **2 次** | 两个变量各提一次就到头：再折腾下去代价成倍涨（解码内存 1.6 MB → 3.7 MB）却未必更清晰，说明掉的不是这两个变量 |
| 整批均值线 | **−3.5%** | 沿用 verify 的"偏糊"判定，避免 export 与 verify 对同一批图给出矛盾结论 |

升档顺序是**先质量、后尺寸**，依据同样是实测：质量档在小图上立竿见影（480 宽 q80 → q90 差 2.3 个百分点），
而尺寸从 960 提到 1440 拿不到边缘能量（都是 98.0%），解码内存却从 1.6 MB 涨到 3.7 MB。
尺寸档在 `--no-resize` / `--max-width` 已经钉住尺寸时不参与升档——提了也不生效，脚本只会提质量。

## 转格式、压尺寸、裁剪是三个独立维度

默认只在**保持源格式**的前提下压尺寸；转格式（`--format webp` / `--format avif`）是显式动作，
通常也是体积收益最大的一步。三个维度可任意组合，也可以只做其中一件。数据来自真实照片型素材：

| 目标 | 命令 | 实测结果 |
| --- | --- | --- |
| **压尺寸，保持源格式**（默认就是它） | `--no-crop --max-width 960` | 六张 341 KB → **208 KB**，解码 59.9 MB → 9.5 MB |
| **压尺寸 + 转 WebP**（不裁剪） | `--format webp --no-crop --max-width 960` | JPEG 1208 KB → **42.5 KB（−96%）**，解码 17.4 MB → 2.0 MB |
| **压尺寸 + 裁剪 + 转 WebP** | `--format webp` + `--box/--dpr` | JPEG 1208 KB → **40.3 KB（−97%）**，解码 17.4 MB → 1.6 MB；六张 341 KB → 195 KB |
| 只转 WebP（不动尺寸、不裁剪） | `--format webp --no-crop --no-resize --quality 90` | JPEG 1208 KB → **259.8 KB（−78%）**；PNG 11.1 MB → 660 KB（−94%），尺寸与解码内存不变 |
| 只转 WebP 且零损失 | 同上换 `--lossless` | PNG 11.1 MB → 无损 WebP 8.5 MB（−24%），像素完全一致 |
| 转 AVIF | `--format avif --quality 60` | JPEG 1.2 MB → 112.8 KB（−91%）；需 Pillow 支持，脚本会自检 |
| 保留原格式与分辨率、只裁剪 | `--no-resize --box 240x108` | 六张 341 KB → **510 KB（反而变大）**，解码 59.9 MB → 46.1 MB |

默认组合 = 裁剪到显示比例 + 缩到屏上像素宽的 2 倍（给 `--box` / `--dpr`），也就是在第一行的基础上
多一步裁剪。保持源格式与转 WebP 是两组独立测量，别互相换算。

由以上实测数据得出的边界结论（写在 SKILL.md 里当规则用）：

1. 只裁剪通常得不偿失：保持原分辨率裁剪，体积因重新编码变大（+49%），解码内存只降 23%
2. 转格式不等于变小：纯色/线条/截图转 JPEG 会变大（1.4 KB → 21 KB），照片类转 WebP/AVIF 才有明显收益
3. 只转格式不降解码内存：解码内存只跟像素数有关，想省内存必须降尺寸
4. 别把照片转 PNG：连续色调下反而暴涨（109 KB → 1.6 MB）

## 复现方式

```bash
SKILL_DIR="${CODEX_HOME:-$HOME/.codex}/skills/image-tools"
S="$SKILL_DIR/scripts/optimize_images.py"

python3 "$S" analyze  <素材目录> --box 240x108 --dpr 2
python3 "$S" export   <素材目录> --out /tmp/img-out --box 240x108 --dpr 2 --supersample 2 --quality 90
python3 "$S" verify   <素材目录> /tmp/img-out --box 240x108 --dpr 2
```

换素材后结论可能变化：照片类收益大，纯色、线条、截图类另说。

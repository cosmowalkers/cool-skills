# commit-message｜提交规范

本 skill 固化两件事：**commit message 怎么写**，以及**混在一起的改动怎么拆成可独立回滚的提交**。
解决的问题是提交记录只有一行「优化代码」——三天后没人说得清它改了什么、影响了谁、要不要回归。

产出的 message 固定包含四件套：**修改目的 / 影响范围 / 改动范围 / 测试建议**，
配合类型前缀（`perf`、`feat`、`fix`……）和模块 scope。

## 一、能做什么

| 你想做的事 | 这样说就行 | 它会怎么做 |
| --- | --- | --- |
| 提交当前改动 | 「把这批改动提交了」 | 盘出改动、按意图分组、逐组提交，每条 message 带完整四件套 |
| 改动混在一起想拆开 | 「这次改的东西太杂，帮我拆成几个提交」 | 按「能否独立回滚」分组；同一文件跨组的按 hunk 拆，不整文件带过去 |
| 只想要 message | 「这几个改动帮我写 commit message，先别提交」 | 只给 message 文本，不动 git |
| 让 AI 先给自己看 | 「message 写好给我过目」 | 先贴完整 message 等你确认，确认后才执行 |
| 补写历史 message | 「这条提交的 message 补一下影响范围」 | 按模板给出修改后的完整 message，改历史仍由你决定 |

## 二、怎么用

一句自然语言就够：

- 「把这次改动提交了，按规范拆一下」
- 「commit message 先给我看，别提交」
- 「这次改了依赖、图片和渲染三块，拆成三个提交」

有三件事值得先知道：

1. **它默认不提交。** 只有你明确说「提交」它才动 git；你没授权时它只给方案和 message。
2. **push 是单独一步。** 提交完不会顺手推，要推得再说一次。
3. **它不会顺手夹带。** 无关文件、无关 imports 的格式改动不会被塞进本次提交。

## 三、message 长什么样

```
<type>(<scope>): <一句话说明目的，≤ 50 字>

【修改目的】
为什么改：解决什么问题 / 什么指标变差 / 什么需求驱动。有数据就带上。

【影响范围】
用户可感知还是仅构建期；影响哪些页面、模块、环境、浏览器；有无行为变化。

【改动范围】
- <文件或模块>：<改了什么>

【测试建议】
- <可执行的验证步骤：命令 + 预期结果>
```

类型用 `feat` / `fix` / `perf` / `refactor` / `docs` / `test` / `build` / `ci` / `chore` / `style` / `revert`，
scope 取项目里的真实模块名（`deps`、`img`、`render`……）。

## 四、为什么这么要求

| 字段 | 回答谁的什么问题 |
| --- | --- |
| 修改目的 | 这个提交该不该跟？是不是我要的那个修复？ |
| 影响范围 | 上线要不要特意回归？影响用户还是只影响构建？ |
| 改动范围 | 出问题时该看哪些文件？能否只回滚这一块？ |
| 测试建议 | 换个人接手，怎么复现验证？ |

**拆分粒度**的判据只有一条：能不能独立回滚。回滚粒度粗的代价（连带回退掉好改动、
排查时对着几百行 diff 猜）永远大于提交数多带来的那点阅读成本。

## 五、局限

- 不替你决定「该不该提交」，也不替你 push。
- 不做代码审查，不判断改动本身对不对。
- 不负责建分支、开 PR、改历史提交（amend / rebase 由你决定后再说）。
